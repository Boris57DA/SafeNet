# Настройка на реалната база

1. Влез в https://supabase.com/dashboard с GitHub. New project → име SafeNet Academy → европейски регион. Паролата за базата се пази отделно и не се записва в проекта.
2. В SQL Editor изпълни целия `supabase/schema.sql` **веднъж в празен проект**. Ако получиш `already exists`, не изтривай таблици: провери дали първото изпълнение е успешно. Скриптът е транзакционен.
3. Изпълни `supabase/seed.sql`. Той може да се изпълнява повторно. Създава 3 мисии и 9 избора; опитите се създават от реалната игра, не от измислен потребител.
4. Authentication → Sign In / Providers → Allow anonymous sign-ins: включено. Ако е активирана CAPTCHA, този учебен клиент няма CAPTCHA widget: необходимо е да се добави преди ползване с тази настройка. За публично широко използване добавете CAPTCHA и подходящи лимити.
5. Connect или Settings → API Keys: копирай Project URL и **publishable** ключа (или legacy **anon**). Никога secret/service_role. Попълни `js/config.js`:

```js
export const config = {
  url: 'https://YOUR_PROJECT.supabase.co',
  publicKey: 'sb_publishable_YOUR_PUBLIC_KEY'
};
```

Тези две стойности са предназначени за браузър. Публичният ключ не замества RLS. Не поставяй database password, access token или service_role в този файл.

6. `npm start`, отвори приложението. Надписът трябва да стане „Supabase · свързана база данни“. Ако виждаш „Локално демо“, реалната интеграция не е конфигурирана. При невалидни настройки приложението показва грешка, без тихо преминаване в демо.
7. Отвори мисия, избери отговор. Трябва да пише „Резултатът е записан в Supabase“. В Table Editor → attempts трябва да има нов ред. Изпълни още една мисия за втори тестов запис.
8. Презареди: резултатите остават. Отвори в инкогнито: новият анонимен потребител вижда нулев прогрес. В Dashboard администраторът вижда всички редове; това не е нарушение на RLS.
9. Изпълни `supabase/verify.sql`, експортирай структурата като CSV в `docs/evidence/`, заснеми трите таблици и връзките. Не снимай API Keys или пароли.

## Как работи защитата

Supabase Auth създава анонимен потребител с роля authenticated. Мисиите и видимите полета на отговорите са четими. Правилността и обясненията на choices не са директно достъпни. Attempts се четат само когато auth.uid() = user_id. Клиентът няма директни INSERT/UPDATE/DELETE права. RPC submit_answer определя текущия потребител, проверява избора, изчислява точките и връща опита. Уникалното ограничение предотвратява повторни точки, включително при повторно изпратена заявка.

## Проверки на права

В DevTools Network разгледай реалните заявки, без да публикуваш JWT. GET choices с `select=*` трябва да бъде отказан, а със `select=id,scenario_id,position,text` — разрешен. Опит за POST към attempts трябва да бъде отказан. Два браузърни профила трябва да имат различни user_id и да виждат само собствения си прогрес. Не изключвай RLS, за да „поправиш“ грешка.

## Чести проблеми

- Anonymous sign-ins disabled: включи анонимния вход.
- Няма мисии: изпълни seed.sql.
- Permission denied: провери schema.sql, RLS и column grants.
- Failed to fetch: провери интернет, URL, блокиращ CDN плъгин или спрян Supabase проект.
- Сгрешен ключ: ползвай publishable/anon от същия проект.
- Изчистване на browser storage: губи анонимната сесия; това е ограничение на Етап 2.
